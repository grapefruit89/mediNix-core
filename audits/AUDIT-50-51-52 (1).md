## 1. Executive Summary

**Nicht produktionsreif — der Code evaluiert nicht einmal.** In `52-security` liegen zwei harte Nix-Fehler (`526`: `systemd.services` zweimal im selben Attrset definiert; `520`: Top-Level-`users` neben explizitem `config` → Modulsystem-Reject), in `51-ingress` ein undefinierter Bezeichner (`513: idpDomains`) und ein Enum-Typfehler (`512` setzt `accessGroup = "idp"`, das Enum kennt nur `stream|internal|public`) — jeder einzelne davon killt `nix flake check` sofort. Selbst nach Reparatur der Evaluierung ist die Sicherheitsarchitektur fail-open an mehreren Stellen: der Public-VHost-Guardrail ist eine Tautologie (`auth.mode != "off"` gegen ein Enum ohne `"off"`), Forward-Auth erzeugt einen echten Deadlock (Pocket-ID wird gestartet, sein VHost aber nie publiziert, `forwardAuthUpstream` ist Default `""`), und der Killswitch bindet eine **leere** `resolv.conf` in die isolierten Dienste, was glibc auf `127.0.0.1` zurückfallen lässt — DNS am Tunnel vorbei. `50-core` ist keine Implementierung, sondern ein Manifest, das an vier von fünf Prinzipien nachweislich lügt (nftables-Übernahme, LUKS-Übernahme, "BPF-Verifikation", "keine tote Konfiguration bei Deaktivierung"). Der Repo-eigene Dezimalrahmen-Enforcer in `flake.nix` matcht auf `^[0-9]{3}-` gegen zweistellige Ordnernamen und ist damit garantiert grün, ohne je etwas zu prüfen.

## 3. P0 — Sicherheitslücken, Deadlocks, Fail-Open, Evaluierungsfehler

### P0-1 · `52-security/526-vpn-killswitch.nix` · `config` — `systemd.services` doppelt definiert
**Beweis** — Zeile 121 und Zeile 171 im *selben* Attrset (`config = lib.mkIf ... { ... }`):
```nix
systemd.services."medinix-vpn-route" = { ... };      # 121
...
systemd.services = lib.mapAttrs (name: v: { ... }) activeInstances;   # 171
```
**Impact:** Nix merged Attributpfade nur, wenn *beide* Seiten Attrset-**Literale** sind. Die zweite Zuweisung ist eine Funktionsanwendung → `attribute 'services' already defined`. Der gesamte Killswitch — und damit das gesamte Flake — evaluiert nicht.
**Fix:**
```nix
systemd.services = lib.mkMerge [
  { "medinix-vpn-route" = { /* ... unverändert ... */ }; }
  (lib.mapAttrs (_: _: {
    requires = [ "medinix-vpn-route.service" ];
    after    = [ "medinix-vpn-route.service" ];
    serviceConfig.BindReadOnlyPaths =
      [ "/etc/medinix-killswitch-resolv.conf:/etc/resolv.conf" ];
  }) activeInstances)
];
```

### P0-2 · `52-security/520-core-security.nix` · Modul-Toplevel — `users` neben `config`
**Beweis** — Zeilen 17–25:
```nix
{

  users.users.media = { isSystemUser = true; group = "media"; };

}
```

### P0-5 · `51-ingress/512-pocket-id.nix` · `systemd.services.pocket-id` — serviceConfig-Kollision mit nixpkgs

### P0-6 · `51-ingress/511-caddy.nix` + `512-pocket-id.nix` — Forward-Auth-Deadlock
**Beweis** — `512` Z. 33: `active = cfg.pocketId.enable || cfg.ingress.auth.mode == "forward-auth";`
`511` Z. 29–34: `enabled = cfg.${n}.enable or cfg.${lib.toCamelCase n}.enable or false;` → für `pocket-id` wird `cfg.pocketId.enable` gelesen.
`default.nix` Z. 413–417: `forwardAuthUpstream = lib.mkOption { type = str; default = ""; };`
**Impact:** Bei `auth.mode = "forward-auth"` **ohne** `pocketId.enable = true` läuft der IdP, sein VHost wird aber nie publiziert → niemand erreicht die Login-Seite → alle `public`-Dienste sind hart ausgesperrt. Gleichzeitig rendert `mkBaseConfig` `forward_auth  { uri /oauth2/auth … }` mit leerem Upstream → **ungültiges Caddyfile, Caddy startet nicht**. Caddy zeigt zu keinem Zeitpunkt auf `registry."pocket-id".port` — die Kopplung existiert nur im Kommentar (`512` Z. 26–27, `70`).
**Fix:**
```nix
# 512-pocket-id.nix — IdP ist aktiv ⇒ Upstream ist bekannt
medinix.ingress.auth.forwardAuthUpstream =
  lib.mkDefault "http://127.0.0.1:${toString svc.port}";

# 511-caddy.nix — implizit aktivierte Dienste mit einbeziehen
enabledServices = lib.filterAttrs (n: _:
  ((cfg.${n}.enable or cfg.${lib.toCamelCase n}.enable or false)
   || (n == "pocket-id" && ing.auth.mode == "forward-auth"))
  && (registry.${n}.port or null) != null
) ing.vhosts;

# + Assertion
{ assertion = ing.auth.mode != "forward-auth" || ing.auth.forwardAuthUpstream != "";
  message = "[ingress] forward-auth aktiv, aber forwardAuthUpstream ist leer (Fail-Open/Caddy-Startfehler)."; }
```

### P0-7 · `52-security/526-vpn-killswitch.nix` · `environment.etc."medinix-killswitch-resolv.conf"` — DNS-Leak am Tunnel vorbei
**Beweis** — Z. 39–42 `dnsServers = lib.mkOption { … default = []; };`; Z. 166–169 schreibt die Datei aus genau dieser Liste; Z. 175 mountet sie über `/etc/resolv.conf`. `grep -rn "vpnKillSwitch"` findet **keinen einzigen Setter** für `services.vpnKillSwitch.dnsServers` — `525` Z. 22 setzt `medinix.vpn.dnsServers`, ein anderer Optionspfad.
**Impact:** Die gemountete `resolv.conf` ist leer. glibc fällt bei fehlendem `nameserver` auf `127.0.0.1` zurück. Die `mark_*`-Chain akzeptiert `ip daddr 127.0.0.0/8` **vor** dem Marking (Z. 85) → die Query geht an den lokalen Resolver, der unter fremder UID läuft, ungemarkt, über `eth0`. Das ist exakt der Leak, den ADR-5260 Pillar 3 auszuschließen behauptet. Fail-Open.
**Fix:**
```nix
# 526: Datei nur schreiben, wenn sie sinnvoll ist, sonst hart failen
assertions = [ {
  assertion = cfg.dnsServers != [];
  message = "[vpnKillSwitch] dnsServers ist leer — /etc/resolv.conf wäre leer und glibc fällt auf 127.0.0.1 zurück (DNS-Leak).";
} ];
# 525-vpn-interface.nix: Brücke schlagen
services.vpnKillSwitch.dnsServers = lib.mkDefault vpn.dns;
services.vpnKillSwitch.vpnInterface = lib.mkDefault ifName;
```

### P0-9 · `59-guardrails/590-guardrails.nix` · `INV-PUBLIC-TLS-AUTH` — Tautologie, Guardrail ist fail-open
**Beweis** — Z. 33:
```nix
(cfg.ingress.tls.mode != "off" &&
 (cfg.ingress.auth.mode != "off" || cfg.ingress.allowPublicUnauth == true))
```
`default.nix` Z. 410: `mode = lib.mkOption { type = lib.types.enum [ "none" "forward-auth" ]; default = "none"; };`
**Impact:** `"off"` ist kein zulässiger Wert → `auth.mode != "off"` ist **immer wahr**. Der Auth-Teil des Invariants prüft nichts. `accessGroup = "public"` (z. B. `seerr`, Registry `caddyClass = "public"`) wird mit `auth.mode = "none"` ins WAN publiziert — `mkBaseConfig.public` rendert dann `authBlock = ""`. Zusätzlich verdeckt die Kurzschluss-Auswertung die **Phantom-Option** `cfg.ingress.allowPublicUnauth`, die in `default.nix` nicht existiert; würde die linke Seite je falsch, gäbe es einen Eval-Fehler statt einer Assertion.
**Fix:**
```nix
(reg.mkInvariant "INV-PUBLIC-TLS-AUTH"
  (let pub = lib.filterAttrs (_: v: v.accessGroup == "public") (cfg.ingress.vhosts or {});
   in pub == {} || (cfg.ingress.tls.mode != "off" || cfg.ingress.tls.acmeHost != null)
                   && cfg.ingress.auth.mode == "forward-auth"))
```

### P0-12 · `51-ingress/518-landingpage.nix` · `config` — ungeschützte Host-Übernahme + Null-Interpolation
**Beweis** — Z. 106–110:
```nix
config = lib.mkIf (config.services.caddy.enable) {
  services.caddy.virtualHosts."${cfg.domain}" = apexHost;

```
**Impact:** Kein `cfg.enable`, kein `ing.enable`, kein `cfg.domain != null` im Guard. Auf jedem Host mit globalem Caddy schreibt mediNix einen Apex-VHost — auch bei `medinix.enable = false`.     ${tlsDirective}
```nix
    root * ${landingHtml}
    file_server
    ${lib.concatStringsSep "\n" redirs}
  '';

```

### P0-13 · `51-ingress/513-cloudflare-dns.nix` · `script` — DDNS bricht beim ersten Lauf und danach permanent
**Beweis** — Z. 90 `set -euo pipefail`; Z. 99 `if [ -f "$CREDENTIALS_DIRECTORY/cf-ddns-token" ]`; `LoadCredentialEncrypted` steht unter `lib.mkIf (ddns.tokenCredential != null)` (Z. 74). Z. 209:
```bash

```
**Impact:** (a) Ohne `tokenCredential` setzt systemd `CREDENTIALS_DIRECTORY` nicht → `set -u` bricht in Zeile 99 ab, **bevor** der `tokenFile`-Pfad je erreicht wird. if [ -n "$CRED_DIR" ] && [ -f "$CRED_DIR/cf-ddns-token" ]; then
```bash
  TOKEN_FILE="$CRED_DIR/cf-ddns-token"
elif …
…
jq -n --arg wan "$WAN_IP" --arg lan "$LAN_IP" '{wan:$wan,lan:$lan}' > "$STATE_FILE"
```

### P1-1 · `513-cloudflare-dns.nix` — drei Registry-Bypässe in einer Datei

`lib/registry.nix` Z. 59: `cloudflare-dns = mkNoPort "cloudflare-dns" 513 "script" "none";` → `uid = null`, `stateDir = null`, `hardeningProfile = "script"`.
**Impact:** Die Registry ist für diesen Dienst nachweislich nicht die Wahrheit. Zusätzlich Namens-Drift: Registry-Key `cloudflare-dns`, Unit + User heißen `cloudflare-ddns` — `520`s Sudo-Regel (`systemctl restart cloudflare-dns.service`) zielt ins Leere, `mkPeerIsolation` findet den State-Dir nicht.
**Fix:**
```nix
# registry.nix: echten Eintrag geben statt mkNoPort
cloudflare-ddns = (mkService "cloudflare-ddns" 513 "network" "none") // { port = null; };
# 513: uid = reg.uid; stateDir = reg.stateDir; profile = reg.hardeningProfile;
```

### P1-2 · `526-vpn-killswitch.nix` Z. 60 — `networking.nftables.enable = true` bricht Manifest §5
**Beweis:** 52-README: *„global `boot.kernel.sysctl` and default-drop `nftables` configurations were removed to honor Additive Host Integration"* — direkt daneben schaltet das Modul das Firewall-**Backend** des gesamten Hosts um.
**Impact:** Auf einem Host mit iptables-Backend werden dessen sämtliche Regeln stillschweigend ersetzt. Das ist keine additive Integration, das ist eine Übernahme. Gleichzeitig fordern `590-guardrails.nix` Z. 120 und `592-security-guardrails.nix` Z. 42/46 (`INV-FW-01`, `INV-TECH-04`) `networking.nftables.enable` **immer**, während `526` es nur bei aktiven Instanzen setzt → eine Config mit `medinix.enable = true` und ohne SABnzbd ist nicht baubar.
**Fix:** `networking.nftables.enable` als `assertion` formulieren, nicht als `config`-Setzung; `INV-FW-01` auf `activeInstances != {}` konditionieren; `INV-FW-01` in einer der beiden Guardrail-Dateien löschen (Duplikat).

### P1-3 · `526-vpn-killswitch.nix` Z. 66–69 — tautologische Assertion
**Beweis:** `assertion = lib.all (n: lib.hasAttr n config.systemd.services) (lib.attrNames activeInstances);` — dieselbe Datei legt diese Units in Z. 171 selbst an.
**Impact:** Das Guardrail kann per Konstruktion nie feuern. Ein Tippfehler in `instances.<name>` erzeugt still eine Geister-Unit statt eines Fehlers.
**Fix:** gegen `config.systemd.services` *vor* der eigenen Definition prüfen ist nicht möglich — stattdessen den Instanznamen aus der Registry ableiten: `assertion = lib.all (n: registry ? ${n}) (lib.attrNames activeInstances);`

### P1-4 · `526-vpn-killswitch.nix` — `ipv6`-Option ist tot
**Beweis:** Mark-Tabelle Z. 73 `family = "ip";` — es gibt keine `ip6`- oder `inet`-Mark-Chain. Der `cfg.ipv6`-Zweig (Z. 149–161) legt `ip -6 rule fwmark …` an, aber **nichts markiert je ein v6-Paket**.
**Impact:** Kein IPv6-Leak (die `inet`-Kill-Chain droppt v6 mangels Mark), aber die Option suggeriert IPv6-Tunneling, das es nicht gibt. Wer sie einschaltet, glaubt an v6-Konnektivität und bekommt schwarze Löcher.
**Fix:** Mark-Tabelle auf `family = "inet"` heben und `meta mark set` für beide AF setzen, oder `ipv6` entfernen und in der Kill-Chain `meta nfproto ipv6 drop` explizit dokumentieren.

### P1-5 · `526` Kill-Chain Z. 108–109 — Loopback-Blanket-Accept als Killswitch-Umgehung
**Beweis:** `oifname "lo" accept` + `ip daddr 127.0.0.0/8 accept` in **beiden** Chains, ohne Port-Einschränkung.
**Impact:** Antwort auf „Kann ein isolierter UID über 127.0.0.1:Caddy ins WAN?" — über Caddy allein nein (reiner Reverse-Proxy auf `127.0.0.1`-Upstreams). Aber SABnzbd (UID 5410) erreicht ungehindert **jeden** Loopback-Dienst, u. a. Prowlarr (`127.0.0.1:5360`, Profil `dotnet` → `networkPolicy.internet`, also voller WAN-Egress) — ein Indexer-Proxy ist per Definition ein Fetch-Primitiv. Damit existiert ein UID-übergreifender WAN-Relay am Killswitch vorbei.
**Fix:**
```nft
# nur das, was wirklich gebraucht wird
ip daddr 127.0.0.1 tcp dport { 5410 } accept   # eigenes Web-UI
ip daddr 127.0.0.1 udp dport 53 accept          # nur wenn dnsServers lokal
```

### P1-6 · `511-caddy.nix` Z. 164–167 — CrowdSec-Plugin bricht „Caddy bleibt flach" **und** baut nicht
**Beweis:**
```nix
services.caddy.package = lib.mkIf (cfg.observability.crowdsec.enable) (pkgs.caddy.withPlugins {
  plugins = [ "github.com/hslatman/caddy-crowdsec-bouncer@latest" ];

```
**Impact:** Drei Fehler übereinander: (a) L7-Ban-Plugin in Caddy verstößt gegen die Flat-Caddy-Regel — der Ban-Hammer gehört zu `582-crowdsec.nix`/nftables; (b) `lib.fakeSha256` garantiert `hash mismatch` → Build bricht ab, sobald CrowdSec aktiv ist; (c) `@latest` ist nicht reproduzierbar. Zusätzlich wird in keinem Template je eine `crowdsec`-Direktive emittiert → das Plugin wäre selbst nach erfolgreichem Build funktionslos, und im Standalone-Modus startet `511` ohnehin `${pkgs.caddy}/bin/caddy` (Z. 143), also das Paket **ohne** Plugin.
**Fix:** Block ersatzlos streichen. `582-crowdsec.nix` liefert bereits `crowdsec-firewall-bouncer` mit `mode = "nftables"`.

### P1-7 · `582-crowdsec.nix` Z. 33–46 — Ban-Hammer ist fail-open
**Beweis:** `nftables.ipv4.set-only = true; table = "medinix_security";` — eine Tabelle `medinix_security` wird nirgends im Repo angelegt (`grep` bestätigt: nur hier). Der Kommentar Z. 59 („Bouncer for nftables is handled by Caddy plugin") widerspricht Z. 33 in derselben Datei.
**Impact:** `set-only` pflegt nur Sets und erwartet, dass jemand anderes sie in einer Chain referenziert. Niemand tut das → Bans werden nie durchgesetzt.
**Fix:** `set-only = false` (Bouncer legt Tabelle+Chain selbst an) oder in `52-security` eine `medinix_security`-Chain mit `ip saddr @crowdsec-blacklists drop` ergänzen — und den Kommentar korrigieren.

### P1-8 · `583-runtime-guard.nix` Z. 35–41 — prüft eine Tabelle, die es nicht gibt
**Beweis:** `nft list table inet medinix_vpn` bzw. `nft list chain inet medinix_vpn killswitch` gegen `526` Z. 72/95: `medinix_vpn_mark` (family `ip`) und `medinix_vpn_filter` (family `inet`).
**Impact:** Der Runtime-Guard alarmiert bei **jedem** Lauf „CRITICAL: medinix_vpn nftables table missing" und beendet sich mit `exit 1` — echte Leaks gehen im Rauschen unter. Antwort auf „überschreibt etwas in 52 die `medinix_vpn`-Tabelle?": nein, sie existiert schlicht nie.
**Fix:** `nft list chain inet medinix_vpn_filter killswitch` bzw. beide Tabellennamen zentral in `lib/registry.nix` ablegen.

### P1-9 · `511-caddy.nix` Z. 196–197 — Firewall öffnet 443 nicht, wenn ACME das TLS liefert
**Beweis:**
```nix

  (if ing.tls.mode == "off" then [ 80 ] else [ 80 443 ]);
```
`tls.mode` ist Default `"off"`; `tlsDirective` (Z. 106–109) prüft aber `acmeHost` **zuerst**.
**Impact:** Die dokumentierte Konfiguration „`acmeHost` setzen, `tls.mode` unangetastet lassen" erzeugt HTTPS-VHosts hinter einer geschlossenen Firewall. Stiller Totalausfall des Ingress.
**Fix:** `(if ing.tls.mode == "off" && ing.tls.acmeHost == null then [ 80 ] else [ 80 443 ])`

### P1-10 · `hardening-profiles.nix` `network` — `PrivateUsers = true` + `CAP_NET_BIND_SERVICE`
**Beweis:** `base` Z. 62 `PrivateUsers = true;`, `network` Z. 109–110 `AmbientCapabilities/CapabilityBoundingSet = "CAP_NET_BIND_SERVICE"`. `caddy-media` bindet :80/:443 (Z. 196–197).
**Impact:** Bei `PrivateUsers=yes` wirken Capabilities nur im Child-User-Namespace; der Host-Netns gehört dem initialen Namespace. `bind(:80)` scheitert mit `EACCES`. Standalone-Caddy startet nicht.
**Fix:** `network = base // { PrivateUsers = false; … }` oder Sockets via `systemd.sockets` mit `ListenStream=80` (Socket-Activation, kein Cap nötig).

### P1-11 · `514-acme.nix` Z. 73 — `email = "admin@${cfg.domain}"` ohne Null-Guard
**Beweis:** Der `mkIf`-Guard (Z. 59) prüft `acmeHost != null`, nicht `cfg.domain != null`.

### P1-12 · `513` ↔ `514` ↔ `591` — drei verschiedene Wahrheiten über den Cloudflare-Token
**Beweis:** `514` Z. 44–48 Priorität `acmeCredential > cloudflareTokenCredential > tokenCredential > tokenFile`. `513` Z. 74 liest **ausschließlich** `ddns.tokenCredential`. `591` `DNS-001` (Z. 39–43) akzeptiert alle drei.

### P1-13 · `520-core-security.nix` Z. 34–44 — Sudo-Regeln zielen auf falsche Units, Wildcard zu breit
**Beweis:** `restartCmds` wird aus `registry.services.*.unitName` erzeugt. Registry kennt `caddy` (reale Unit im Standalone-Modus: `caddy-media`) und `cloudflare-dns` (reale Unit: `cloudflare-ddns`). Z. 43: `NOPASSWD: /run/current-system/sw/bin/systemctl status * --no-pager`.
**Impact:** Break-Glass kann Ingress und DDNS **nicht** neustarten — genau die zwei Dienste, wegen derer man sich aussperrt. Der `*`-Wildcard matcht in sudoers beliebige Argumente inklusive Leerzeichen, also auch `-H user@host` / `-M container`, und weitet den Break-Glass-Pfad über „status" hinaus.
**Fix:** `unitName` in der Registry auf die real erzeugten Units korrigieren; Wildcard durch explizite Unit-Liste ersetzen (`systemctl status sonarr.service`, …) und `--no-pager` voranstellen.

### P1-14 · `520-core-security.nix` — README-Behauptung ohne Implementierung

### P1-15 · `528-fde-tpm2.nix` Z. 34–39 — Übernahme des physischen Layers

### P1-18 · `513` Z. 204–207 — RFC1918-Adressen in der öffentlichen Zone

### P1-19 · `525-vpn-interface.nix` Z. 26–33 — stille Fehlkonfiguration statt Assertion
**Beweis:** `privateKeyFile = credMount;` unabhängig davon, ob `LoadCredentialEncrypted` gesetzt wurde (Z. 36–41 steht unter `mkIf (vpn.privateKeyCredentialPath != null)`); `peers = lib.optional (vpn.peer.publicKey != "") { … }`.


## 6. Antworten auf die Spezialfragen (kompakt)

**50 ↔ 51/52** — Das Manifest behauptet BPF-Verifikation im Killswitch (existiert nicht), `RestrictNetworkInterfaces` als Isolationsmechanismus (von ADR-5260 verworfen), registry-exklusive `caddyClass` (in `512`/`581` gebrochen), Nicht-Übernahme von Host-Firewall und physischem Layer (durch `526` bzw. `528` gebrochen), und restlose Entfernbarkeit (durch `518` und `520` gebrochen). **Niemand importiert `50-core` als Code.**

**51 intern** — Pocket-ID-VHost wird nur bei `pocketId.enable` publiziert, während `forward-auth` den IdP implizit startet → **Deadlock bestätigt (P0-6)**. Caddy zeigt **nicht** auf `registry."pocket-id".port`, sondern auf `forwardAuthUpstream` mit Default `""` — die Kopplung existiert nur im Kommentar. ACME nutzt `LoadCredentialEncrypted` + `EnvironmentFile` auf den *entschlüsselten* Runtime-Pfad — das ist korrekt, aber der Klartext-Fallback `tokenFile` untergräbt Manifest §4. `proxied=true` tritt **nirgends** auf — ADR-5130 wird eingehalten. Doppelte VHost-Merges: ja, wörtlich in `555-seerr.nix`. `accessGroup = "public"` ohne Auth: möglich, weil das Guardrail tautologisch ist. HSTS/Rate-Limit in Caddy: nicht vorhanden — aber das CrowdSec-**Plugin** verstößt gegen die Flat-Caddy-Regel.

**52 intern** — `networking.nftables.enable` wird gesetzt (Z. 60), die Tabellen werden also geladen — der `inet`-Filter hat korrekt eine `filter`-Chain, die `route`-Chain sitzt korrekt in der `ip`-Tabelle. **Keine unzulässige route-chain.** LAN-Allowlist: `allowedLanCidrs` ist default `[]` und wird von `541` nicht gesetzt — kein `192.168.0.0/16`-Bypass im Ist-Zustand, aber die Option erlaubt ihn ohne jede Validierung. `oifname wg0 accept` steht korrekt **hinter** `meta mark ${mark}` — die Mark+Route-Invariante ist gewahrt. IPv6: kein Leak (v6 wird mangels Mark gedroppt), aber die `ipv6`-Option ist funktionslos. Rebuild/Reconnect: `Requires`-Kette `nftables → medinix-vpn-route → sabnzbd` propagiert Stops korrekt; kein `ExecStop` → fail-closed. sudo: `systemctl status *` ist zu breit und die Restart-Liste zielt auf falsche Unit-Namen. **SABnzbd-UID: korrekt** — `541` Z. 107 `uid = uid` aus `registry.sabnzbd.uid` = 5410, `599` VPN-010 verifiziert es zusätzlich.

**51 ↔ 52** — nftables sperrt Caddy nicht aus: `medinix_vpn_filter` hängt ausschließlich am `output`-Hook und filtert nur `skuid`-Treffer; Inbound 80/443 ist unberührt. Ein isolierter UID kommt über Caddy selbst nicht ins WAN, wohl aber über andere Loopback-Dienste (P1-5). Trust-Modelle widersprechen sich: `ingress.trustedCidrs` (RFC1918 + CGNAT, korrekt breit) vs. `allowedLanCidrs` (leer, per-Instanz) — zwei unabhängige Modelle ohne gemeinsame Quelle. CrowdSec überschreibt `medinix_vpn_*` nicht (eigene Tabelle `medinix_security`), aber diese Tabelle wird nie angelegt.

## 7. Priorisierte Reparaturreihenfolge

1. **Evaluierung herstellen.** `526` (`systemd.services` → `mkMerge`), `520` (Modul-Syntax), `513` (`idpDomains`), `555` (doppelte VHost-Zeile). Ohne diese vier Fixes ist jede weitere Aussage über Laufzeitverhalten Spekulation.
2. **`accessGroup`-Enum um `idp` und `none` erweitern**, `511` um ein `none`-Template ergänzen, Registry-`caddyClass` für `pocket-id`/`ntfy` korrigieren.
3. **Forward-Auth-Deadlock schließen.** `forwardAuthUpstream` aus `registry."pocket-id".port` ableiten, implizit aktivierte Dienste in `enabledServices` aufnehmen, Assertion gegen leeren Upstream.
4. **Killswitch verkabeln.** `525` setzt `services.vpnKillSwitch.vpnInterface` und `.dnsServers`; Assertion auf nicht-leere `dnsServers`; Loopback-Accept auf konkrete Ports einschränken.
5. **TLS im Standalone-Modus reparieren.** `caddyUnit`-Ableitung in `514` für `group` und `reloadServices`; `network`-Profil `PrivateUsers = false`; Firewall-443-Bedingung um `acmeHost != null` erweitern.
6. **Fail-open-Guardrails korrigieren.** `INV-PUBLIC-TLS-AUTH` (Tautologie + Phantom-Option), `VPN-011` vs. `536` entscheiden, `INV-FW-01` konditionieren und entduplizieren, `DNS-001` an die tatsächliche Token-Kaskade koppeln.
7. **SSoT wiederherstellen.** `513` vollständig aus der Registry speisen (UID, StateDir, Profil, Unit-Name); `pocket-id.dataDir = svc.stateDir`; `520`-Sudo-Liste gegen reale Unit-Namen.
